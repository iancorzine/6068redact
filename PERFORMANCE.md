# Performance: 5,000-page test

All test files are **synthetic**, generated by `tests/perf/make-big.ts` from invented people. Every page contains the protected person's name, DOB, identifiers and address, plus physician and clinical content. Scanned pages are JPEG images with speckle noise and an invisible OCR text layer (a third of them with OCR errors such as "Vantre1ght").

Machine: Apple M5 Max, 128 GB RAM, macOS 27.0.1. Browser: Playwright Chromium (headless shell 153). Node 22.23. Measured on 2026-10-06.

## Results

| Test file | Where | Time | Pages/s | Peak WASM heap | Peak memory (process) | Output |
|---|---|---|---|---|---|---|
| **1.56 GB**, 5,000 pages, 50% scanned at 300 dpi | Browser (Chromium) | **400.7 s (6.7 min)** | 12.5 | **589 MB** | 2,872 MB (all Chromium processes) | 1.51 GB, 5,000 pages |
| 1.56 GB, same file | Node (same engine code) | 393.0 s | 12.7 | 589 MB | 867 MB (RSS) | 1.51 GB, 5,000 pages |
| 381 MB, 5,000 pages, 60% scanned at 200 dpi | Browser (Chromium) | 172.4 s (2.9 min) | 29.0 | 409 MB | 2,173 MB (all Chromium processes) | 455 MB* |
| 381 MB, same file | Node | 172.9 s | 28.9 | 409 MB | 1,774 MB (RSS)* | 455 MB* |

\* Measured before two later improvements: re-encoding JPEGs at their original quality, and streaming the output to disk. Both reduce output size and memory.

Every run checked the output: the page count matched, and text sampled from every 97th page contained none of the protected strings. Redactions in the 1.56 GB file: 11,250 names, 1,250 SSNs, 1,250 driver's licenses, 1,250 CII, 7,500 account numbers, 5,000 DOBs, 1,250 addresses, 2,500 phones, 2,500 other entries. No page needed the MuPDF image fallback.

## Memory notes

* The **WASM heap** (MuPDF's memory, hard limit 2 GB) peaked at 589 MB on the 1.56 GB file, because the input is read on demand and output chunks leave WASM right away. It rises slowly over a run: 409 MB on the 381 MB file and 589 MB on the 1.56 GB file, in steps of the WASM memory growth size. I did not pin down the exact source; the clear leaks I found are fixed and covered by a regression test. Either way it stays far below the 2 GB limit.
* In the browser, the output is written to the browser's private storage on disk as it is produced. Peak Chromium memory (2.9 GB, the sum over all Chromium processes including the browser and GPU process) is mostly the renderer's JavaScript heap and system allocations. It is not the PDF itself.
* Most of the time goes to redaction, mainly decoding and re-encoding the scan images of pages that have hits. The pre-check text pass is comparatively quick.

## Limits

* **Input files must be under 2 GB.** mupdf.js passes file sizes and offsets as 32-bit integers. Larger files are rejected with a message to split them in Acrobat.
* The output is about the size of the input. If the browser lacks the disk space or storage quota to hold it (private/incognito windows have small quotas), the app reports an error instead of producing an incomplete file.

## Reproduce

```sh
npx tsx tests/perf/make-big.ts /tmp/perf-heavy.pdf 5000 300 0.5 0.1   # ~1.6 GB
npx tsx tests/perf/perf-node.ts /tmp/perf-heavy.pdf
PERF_FILE=/tmp/perf-heavy.pdf npx playwright test perf
```
